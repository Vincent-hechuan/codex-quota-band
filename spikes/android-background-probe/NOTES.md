# Android 后台存活探针记录

状态：构建通过；目标配置下的短时锁屏和手环通知转发测试通过。

## 已验证

- 使用本机便携 JDK 17、Android SDK 36 和 Gradle 9.1 构建成功。
- 探针不声明 `Service` 或前台服务，不创建常驻状态通知。
- 进程在后台时接收 `needs_authorization` 和 `waiting_review` 事件才尝试发通知。
- Android 13 及以上未授予通知权限时，仅记录事件，不让权限异常中断连接循环。
- 调试 APK：`app/build/outputs/apk/debug/app-debug.apk`。

用户随后澄清三项均未设置，因此以下结果只能说明默认系统限制下的行为，不能
用于判断目标配置是否可行。

- 锁屏状态为 `Dozing`，通知权限已授予。
- Android 进程测试结束时仍存在，PID 未变化。
- 手机共记录 7 条事件：处理中 3、需要授权 2、等待查看 2。
- 最后一条记录时间为 13:25:57（北京时间）。
- 电脑端约 13:27:59 观察到客户端断开。
- 此后电脑继续每 15 秒产生测试事件，但客户端数始终为 0。
- 截至 13:32:14，手机事件计数没有继续增长，也没有自动重连。
- 测试服务器已停止，ADB reverse 已移除；探针 APK 保留。

结论：默认系统设置下，普通 Application 后台线程不能在锁屏 Doze 中维持
持续局域网 TCP 接收。目标配置下的门槛结论作废，必须在三项设置完成后重测。

详细原始结果见 `PROTOTYPE-result.txt` 和 `PROTOTYPE-server.log`。

## 2026-07-24 目标配置短时锁屏结果

用户明确完成后台加锁、允许自启动和电池策略无限制后重新测试。系统侧确认通知
权限已授予、后台 AppOp 默认为允许，并且应用已进入 device-idle 用户白名单。

- 正式锁屏起点：13:37:29，事件总数 14。
- 补测终点：13:44:51，事件总数 44，净增长 30。
- 所有定时采样均为 `Dozing`。
- Android 进程 PID 始终为 14537。
- 重连次数始终为 1，没有断开或重新连接。
- 电脑端整个测试期间始终记录 `clients=1`。
- 五分钟主测试期间用户曾短暂误亮屏一次；采样时已经恢复 `Dozing`。
- 为补偿短暂亮屏，随后连续补测两分钟，计数从 35 增长到 44，仍无重连。
- 测试结束后服务器已停止，ADB reverse 已移除；探针 APK 保留。

结论：完成三项后台设置后，“无前台服务、无常驻状态通知”的普通应用在本次
短时锁屏测试中可以持续接收局域网事件。该结果满足小玩具阶段的短时可行性
门槛，但不等同于不同 Android 系统或连续四小时的可靠性承诺。

## 2026-07-24 小米运动健康通知转发结果

探针改用新的通知通道进行定向复测，并记录通知尝试、提交、失败、权限缺失和
前台静默计数。Android 系统确认两类通知均已成功提交；通知读取总权限也已授予
小米运动健康。

首次测试时手环没有收到通知。根因不是后台连接或通知发送失败，而是小米运动
健康默认不会自动转发新安装应用的通知。用户在小米运动健康的应用通知列表中
手动勾选「Codex 后台探针」后再次测试：

- 手环收到「等待查看」。
- 手环收到「需要授权」。
- 两条通知均触发手环震动。
- 测试结束后定向服务器已停止，ADB reverse 已移除；探针 APK 保留。

结论：Android 原生通知 → 小米运动健康 → 小米手环 10 的链路可行。正式安装
流程必须引导用户在小米运动健康中勾选「Codex额度」；仅授予 Android 通知权限
还不够。手环收到任意转发通知都会震动，当前不再承诺按通知类型分别控制静默
和震动，也不为此继续投入探针时间。
