# Codex Hook 状态覆盖 Spike

状态：门槛部分通过，等待产品范围决策

日期：2026-07-24

本机 Codex Desktop：`26.715.10079.0`

## 问题

只使用官方 Codex 生命周期 Hook、且不读取或分析完整助手回复时，能否可靠提供产品计划中的四种任务状态：

- 正在处理
- 已完成
- 需要处理
- 任务受阻

## 验证来源

- 本机当前官方 Codex Manual 中的 Hooks 章节。
- 当前官方 Hook 文档：`https://learn.chatgpt.com/docs/hooks.md`。
- 下载文档 SHA-256：`C2A29DC717985236028E2D3CC3AF42CC39814A56CC52C0D20B1A9A9FA1060D19`。

文档已经完整定义当前发布版的事件与字段，因此先执行协议门槛检查。若协议本身没有所需终态，安装事件记录脚本也无法制造该语义，故本次没有修改全局 Hook 或要求用户进行无意义的信任操作。

## 当前官方事件覆盖

| 产品需要 | 官方 Hook 证据 | 结论 |
| --- | --- | --- |
| 对话身份 | 所有事件包含 `session_id` | 可可靠获取 |
| 同一轮身份 | Turn 级事件包含 `turn_id` | 可可靠获取 |
| 开始处理 | `UserPromptSubmit` | 可可靠获取 |
| 工具活动摘要 | `PreToolUse` / `PostToolUse` 包含 `tool_name` | 可映射安全摘要，但 Hosted Tools 不保证覆盖 |
| 等待权限批准 | `PermissionRequest` | 可可靠识别这一类“需要处理” |
| 轮次停止 | `Stop` | 可可靠知道本轮不再执行 |
| 已完成 | 没有独立终态；`Stop` 不提供完成原因 | 不可可靠区分 |
| 普通提问等待用户输入 | 没有独立终态；`Stop` 只附带完整助手消息 | 不读取或分类回复时不可可靠区分 |
| 任务受阻 | 没有独立 `Blocked` 事件或停止原因 | 不可可靠区分 |

## 隐私与真实性边界

`Stop` 提供 `last_assistant_message`，但使用它会扩大已确认的数据读取范围。即使只在 Windows 本地分析后立即丢弃，也只能基于自然语言猜测“完成、提问或受阻”，无法达到 PRD 要求的真实状态语义。

读取 `transcript_path`、解析 Codex 私有数据库、根据错误文本或重试次数推断状态也违反已确认边界，不能作为替代方案。

## 结论

第一项高风险门槛只能部分通过：

- 可以稳定实现对话级的“处理中”。
- 可以稳定识别需要系统权限批准的“需要处理”。
- 可以稳定识别“本轮已停止处理”，但不能把它诚实拆成“已完成”“普通提问等待输入”和“任务受阻”。

在产品状态范围调整前，不应安装全局 Hook，不应继续制作完整任务看板，也不应进入后续正式开发。

## 待决策方向

推荐把 Hook 首版状态收缩为：

- `处理中`
- `需要授权`
- `等待查看`：本轮已经停止，但不宣称是完成、提问还是受阻

通知类型相应收缩为：

- `等待查看`
- `需要授权`

仍保留“仅在 Codex 失焦时”及手机、手环渠道开关。
