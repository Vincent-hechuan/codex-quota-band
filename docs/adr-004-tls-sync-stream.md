# ADR-004：固定身份的 TLS 同步流

状态：已接受（细化 ADR-003）

日期：2026-07-24

## 背景

ADR-003 已确定一次扫码、固定 Windows 身份、加密自动重连。实现还需要明确加密通道、
凭据用途、版本协商和消息顺序，避免 Android 与 Windows 各自形成不兼容的临时协议。

## 决策

- Windows 使用持久化本机身份密钥提供 TLS 1.3 服务；Android 只信任首次二维码中固定的
  Windows 公钥指纹，不信任局域网地址、发现结果或任意自签名证书。
- 首次配对请求也必须经过该固定身份的 TLS 通道。五分钟一次性配对码成功后，Windows
  生成随机长期手机凭据；Android 将其保存到系统安全存储，Windows 只保存验证所需的哈希。
- 配对二维码遵循 `contract/pairing-offer-v1.schema.json`，只包含电脑公钥指纹、五分钟
  六位单次码和最多八个 `wss://私网数字IP:端口/pair` 候选地址；不得包含长期手机凭据。
- 日常同步使用固定证书身份的加密 WebSocket。手机凭据只在已验证的 TLS 通道内用于认证，
  不进入二维码、局域网发现、URL、日志或诊断文件。
- 局域网发现只公布候选地址、端口和非秘密服务标识。Android 必须先匹配已固定的 Windows
  身份，再发送任何凭据或业务数据。
- 加密流使用 `contract/sync-stream-v1.schema.json`。客户端先声明支持的额度和任务协议版本；
  服务端选择双方都支持的版本，否则关闭连接并显示版本不兼容，不按产品显示版本强制断开。
- 每条服务端消息携带随机连接标识和连接内单调序列。新 TLS 连接可以从新序列开始，旧连接、
  重放或乱序消息不能覆盖当前可信状态。
- 心跳只包含协议版本、连接标识、序列和时间，不包含额度、任务、凭据或诊断信息。

## 后果

- Rust 端采用原生 TLS/WebSocket 库，不引入浏览器运行时；Android 端采用支持证书公钥固定的
  原生网络客户端。
- 证书轮换、Windows 重装、手机替换和撤销都必须回到二维码配对，不提供绕过身份检查的
  “仍然连接”按钮。
- 后续实现必须分别测试错误证书、伪造发现、过期配对码、撤销凭据、乱序消息、连接重建和
  协议不兼容；任何失败都不得回退到明文 HTTP。
