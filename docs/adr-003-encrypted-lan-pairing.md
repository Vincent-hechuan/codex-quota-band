# ADR-003：无感加密的局域网配对

状态：已接受

日期：2026-07-24

决策人：用户

接受方案：一次扫码建立设备身份，后续加密自动重连

## 背景

Android 新架构会在可信局域网内传输额度摘要、任务短标题、任务状态和更新时间。电脑 IP 可能变化，手机又需要在后台自动发现并重连，因此不能把 IP 地址当成设备身份，也不能只依赖局域网环境防止窃听或冒充。

用户同时要求配对流程保持简单，不接受证书配置、密码输入或每次启动重新扫码。

## 决策

- Windows 首次启动时生成并持久化本机身份密钥。
- 首次配对二维码携带短期一次性凭据和电脑公钥指纹。
- Android 伴侣 App 扫码确认后，将长期凭据和电脑身份固定信息保存在 Android 系统安全存储中。
- 后续局域网连接必须加密，并验证服务端身份与已配对电脑一致。
- Windows 只保存验证手机所需的信息，并允许用户从托盘撤销已配对设备。
- 地址发现与身份验证分离：局域网发现只负责找到候选地址，不能替代加密身份验证。
- 用户端仍只有打开二维码、扫码并确认连接，不显示浏览器式证书警告，也不要求手动配置证书、密码或 IP。

## 已评估方案

1. 明文 HTTP/WebSocket 加 Bearer 令牌：实现简单，但同一网络上的窃听者可能看到任务标题或截获长期令牌。
2. 每次使用短码配对：凭据生命周期短，但日常摩擦过高，不符合一次配对和自动重连要求。
3. 公共 CA 证书：局域网动态地址和本地域名部署复杂，会把证书与域名管理暴露给用户。
4. 一次扫码固定电脑身份并使用加密连接：实现成本较高，但兼顾自动发现、身份验证、隐私和无感体验。

用户于 2026-07-24 明确选择方案 4。

## 2026-08-12 补充决策：内置扫码与安全手动配对

部分 Android 系统相机不能识别项目的自定义配对链接，因此不再把厂商系统相机作为扫码能力边界：

- Android 使用 App 内置相机与本地随包二维码模型识别配对链接，相机权限只在用户主动选择扫码时请求。
- 保留 6 位一次性配对码作为备用入口，但不恢复旧版“手填 IP + 配对码”的明文或弱身份流程。
- Windows 仅在配对窗口有效期内广播候选电脑指纹、私网 WSS 地址和过期时间；公告不含配对码、长期令牌或账号内容。
- 手动配对时，手机先显示由候选电脑公钥指纹生成的 `XXXX-XXXX` 安全校验码。用户确认与 Windows 一致后，手机才向固定身份的 TLS 端点提交 6 位配对码。
- 二维码与手动路径最终进入同一 `/pair` 协议、尝试次数限制、一次性失效和凭据存储流程。
- Windows 配对窗口保持单实例；重复点击托盘入口不得生成新凭据，只有窗口内的“刷新配对码”会明确作废旧凭据并更新二维码、6 位码与局域网发现公告。
- Android 在新连接完成 WSS 协议协商后立即请求一次当前额度确认；传输在线仍不能冒充“已同步”，只有 Windows 返回有效上游确认后才更新同步胶囊。

## 后果

- Rust Windows 端与 Android 端必须共同实现密钥生成、二维码配对、证书或公钥固定、凭据轮换与撤销。
- 配对、重连、IP 变化、错误电脑冒充、令牌撤销和重装后的恢复都需要自动化测试与真机验证。
- 发现服务被伪造时，客户端必须拒绝连接，而不是向用户弹出“继续信任”一类绕过选项。
- 加密实现不能增加用户日常步骤；如果底层实现需要额外证书操作，应视为不符合本决策。
