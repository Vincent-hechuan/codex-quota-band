# ADR-002：轻量原生 Windows 端

状态：已接受

日期：2026-07-24

决策人：用户

接受方案：重写原生 Windows 托盘程序并移除 Electron

## 背景

当前 Windows 端使用 Electron 43。即使日常只显示托盘图标，也会携带 Chromium、Node 和相关辅助进程；用户实际观察到整个程序占用 500MB 以上内存。

Android 新架构还需要在 Windows 端增加 Codex 桌面任务状态监控、前台焦点判断、手机副屏同步和通知决策。如果继续在 Electron 上叠加功能，现有运行时成本不会自然消失，后续再迁移的成本也会更高。

## 决策

- 重写轻量原生 Windows 托盘程序并移除 Electron，不保留长期运行的 Chromium 进程。
- 使用 Rust 和 Windows 原生 API 实现，不使用 Tauri、WebView 或其他浏览器壳。
- 保持现有安装方式、额度采集、一次配对、撤销授权、暂停同步、立即刷新、开机启动选择和托盘操作语义。
- 新增 Codex 桌面任务监控、前台焦点判断，以及向 Android 伴侣 App 同步额度和任务状态的能力。
- 内存验收统计整个 Windows 程序进程树，而不是只统计某一个子进程。
- 稳定运行时的进程树内存上限为 100MB；具体测量口径和预热时间在实施计划中固定。
- 新版本只面向 Android，不在 Rust Windows 端保留现有 AstroBox Snapshot v1 或其他 iPhone 兼容链路。

## 已评估方案

1. 继续使用 Electron 并做局部裁剪：改动较小，但 Chromium 和多进程运行时仍在，难以对 100MB 上限作出可信承诺。
2. 将后台采集拆成原生服务，同时保留 Electron 设置界面：后台可下降，但安装、进程通信和双运行时维护更复杂，打开设置时仍会产生较大内存开销。
3. 完整迁移为轻量原生托盘程序：迁移成本最高，但运行时最小、Windows 前台窗口识别更直接，也最符合新增任务监控能力。

用户于 2026-07-24 明确选择方案 3。

## 后果

- 现有 JavaScript 额度采集、缓存、配对服务和安全裁剪逻辑需要迁移或以可验证方式复用。
- 必须增加新旧版本数据与配对凭据的迁移测试，避免升级后无故要求用户重新配对。
- 原生托盘菜单和配对界面可以与现有视觉不同，但功能语义与隐私边界不能退化。
- 原生界面使用 Windows 系统控件即可，不要求像素级复刻 Electron 界面。
- 构建、安装包、自动启动、升级和卸载流程需要重新验证。
- 只有整个进程树在约定测量口径下不超过 100MB，内存优化才算验收通过。
- 验收时先预热 10 分钟，在 Codex 桌面、只读 Hook、手机连接与任务同步全部启用的状态下统计整个进程树专用工作集；二维码或诊断窗口关闭后需回落到 100MB 内，连续运行 4 小时的增长不得超过 20MB。
- iPhone 支持暂缓，未来出现真实需求并有开发精力时再单独立项，不让旧协议约束当前 Android 架构。
